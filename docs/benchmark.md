# Сравнение прогнозов

Команда `backtest` сохраняет прежнее поведение: кандидат и прогноз по последнему
значению, по умолчанию 3 последних часовых окна. Новая команда `benchmark`
сравнивает кандидата с тремя простыми прогнозами на 12 последних часовых окнах.
Модель и базовые методы получают одинаковые истории и одинаковые будущие точки
для оценки. Каждая история обрезается строго до начала проверяемого окна.

## Методы

| Имя | Правило | При стандартных настройках |
|---|---|---|
| chronos2 | Готовая модель без дообучения | 288 значений → 12 точек и p10/p50/p90 |
| persistence | Повторяет последнее значение | Одно значение на весь следующий час |
| rolling_mean | Повторяет среднее последних наблюдений | Среднее последних 12 точек / 60 минут |
| seasonal | Повторяет соответствующие точки прошлого периода | Значения в это время предыдущего дня |

В benchmark для суточного метода нужна история не менее 24 часов и шаг,
на который делятся 1440 минут. Если её не хватает, команда завершается
с объяснением до загрузки весов. Интервалы неопределённости базовым методам
не приписываются.

## Запуск в PowerShell

Из корня проекта, после установки окружения по README:

```powershell
.\.venv\Scripts\python.exe -m pregnancy_monitor generate --scenario daily
.\.venv\Scripts\python.exe -m pregnancy_monitor benchmark --input data/synthetic_hr.csv --data-kind synthetic --folds 12
```

Для быстрой проверки без Chronos‑2:

```powershell
.\.venv\Scripts\python.exe -m pregnancy_monitor benchmark --input data/synthetic_hr.csv --backend persistence --data-kind synthetic --output-dir outputs/baseline_benchmark
```

В этом режиме в отчёте будут только три простых метода. Это не запуск Chronos‑2.

Генератор поддерживает четыре инженерных сценария:

| `--scenario` | Что изменяется |
|---|---|
| daily | Исходная суточная кривая с коррелированным шумом |
| trend | К той же кривой добавлен линейный тренд |
| shift | За 4 часа до конца ряда добавлен сдвиг уровня |
| noisy | Добавлен независимый шум |

Сценарии не воспроизводят физиологию беременности. Они проверяют реакцию кода
и прогноза на разные математические свойства ряда. Используйте разные пути
`--output` генератора и `--output-dir` benchmark, чтобы сохранять отдельные прогоны.

## Что читать в отчёте

- `aggregate`: MAE и RMSE в уд/мин по всем проверенным точкам.
- `per_series`: те же показатели по отдельным рядам.
- `per_fold`: показатели в каждом проверяемом часовом окне.
- `per_horizon_minutes`: качество отдельно на 5, 10, …, 60 минутах.
- `coverage_p10_p90`: какая доля фактических значений попала в интервал модели.
- `pinball_loss_bpm`: потери для каждого квантиля; меньше — лучше.
- `comparison`: сравнение кандидата с лучшим простым методом на этой выборке.
  Положительный `mae_improvement_fraction` означает снижение MAE, отрицательный — рост.
  Если ошибка базового метода равна нулю, относительная величина равна `null`.

Лучший базовый метод определяется по тем же проверочным окнам только для
диагностики. Это не независимая оценка выбранного победителя и не механизм
автоматической смены модели в сервисе. `automatic_model_selection` всегда `false`.

Для реальных данных следующий шаг — заранее выделить участниц и будущие периоды
для окончательной проверки, затем подбирать настройки только на оставшейся части.
Отдельно нужны доля отказов по качеству сигнала, задержка и память на целевом сервере.
Клинические критерии должен определять медицинский специалист команды.
