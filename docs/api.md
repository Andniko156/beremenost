# Приватный API прогноза ЧСС

Сервис нужен для проверки серверного контракта будущего приложения Android/iOS.
Он принимает один псевдонимный ряд, строит прогноз и возвращает его сразу с HTTP 200.
Состояние запросов и измерения в БД или файлы сервис не сохраняет. Веса модели
загружаются один раз при старте процесса. Во время работы inference выполняется локально.

## Самая короткая демонстрация

В существующем окружении из README:

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[api,test]"
.\.venv\Scripts\python.exe scripts/demo_api.py --start-server --backend persistence
```

Скрипт создаёт временный сервисный ключ, запускает API на `127.0.0.1:8000`,
отправляет синтетический ряд, сохраняет ответ в `outputs/api_demo/response.json`
и останавливает запущенный процесс. Базовый прогноз позволяет проверить обмен
без скачивания модели. Порт 8000 должен быть свободен.

Для настоящей Chronos‑2 нужны зависимости `[chronos]` и заранее скачанные веса.
Если уже выполнялся прогноз из README, веса доступны в кэше. Затем:

```powershell
$env:OMP_NUM_THREADS = "2"
$env:MKL_NUM_THREADS = "2"
.\.venv\Scripts\python.exe scripts/demo_api.py --start-server --backend chronos2
```

Для отдельной локальной копии весов задайте `PM_MODEL_PATH=models/chronos-2`.
Подготовка копии описана в README. API по умолчанию работает с `PM_OFFLINE=1`:
при отсутствии весов он сообщает о неготовности, а не скачивает их при запросе.
Разрешить загрузку при старте можно через `PM_OFFLINE=0`; сами измерения
в Hub не отправляются.

## Постоянный локальный процесс и Swagger

```powershell
$env:PM_API_TOKEN = (.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(32))").Trim()
$env:PM_BACKEND = "chronos2"
.\.venv\Scripts\python.exe -m pregnancy_monitor serve
```

Пока процесс работает, откройте `http://127.0.0.1:8000/docs`.
Схема доступна через `/openapi.json`, её копия находится в
[openapi.json](openapi.json). В Swagger кнопка Authorize принимает сервисный токен.
Для обращения из другого терминала задайте в нём тот же `PM_API_TOKEN` и выполните
`python scripts/demo_api.py` без `--start-server`.

## Методы

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| GET | /healthz | Процесс жив | Без токена |
| GET | /readyz | Модель загружена и не перешла в состояние ошибки | Bearer |
| POST | /v1/forecasts/heart-rate | Синхронный часовой прогноз | Bearer |

`/healthz` может вернуть 200 при неготовой модели. Для готовности используйте
`/readyz`: он вернёт 503, если веса не удалось загрузить или вычисление сломалось.
После ошибки вычисления нужен перезапуск сервиса; автоматической подмены
Chronos‑2 простым методом нет.

Заголовки запроса:

```http
Authorization: Bearer <service-token>
Content-Type: application/json
```

Структура тела:

| Поле | Значение |
|---|---|
| series_id | Псевдоним: 1–64 латинских буквы, цифры, `_` или `-` |
| data_kind | `synthetic` или `device`, явно указывается отправителем |
| measurements | От 288 до 576 измерений, с регулярным шагом 5 минут |
| measurements[].timestamp | Строка ISO 8601 с `T` и часовым поясом, например `2026-11-04T12:00:00Z` |
| measurements[].heart_rate_bpm | Конечное положительное число в уд/мин |
| measurements[].quality | `valid`, `invalid` или `unknown`; поле обязательно |

Полный корректный запрос формирует `scripts/demo_api.py`. Неизвестные поля
отклоняются. Передавать имя, email или дневник симптомов в этот метод не нужно.

## Техническая проверка истории

Все переданные измерения должны иметь отметку `valid`. История проверяется на
дубли, разрывы, единый ряд и достаточное количество точек. Данные приводятся к UTC
и сортируются; автоматического заполнения пропусков и агрегации здесь нет.
Для прогноза берутся последние 288 точек.

Последняя точка должна быть не старше 15 минут и не более чем на 60 секунд
впереди серверного времени. Это начальная техническая политика прототипа.
Она настраивается через `PM_MAX_AGE_MINUTES` и `PM_FUTURE_SKEW_SECONDS`;
медицинским критерием безопасности эти числа не являются.

Поле `quality` — отметка от отправляющего адаптера. Сервер не анализирует
контакт электрода, ЭКГ или артефакты движения самостоятельно. Надёжный источник
этой отметки предстоит определить после выбора модели VivaLNK.
Проверка давности действует и на синтетику: демонстрационный скрипт ставит
ей свежие временные метки, сохраняя явную пометку `synthetic`.

## Ответ и ошибки

Успешный ответ содержит `series_id`, `data_kind`, `generated_at`,
`forecast_origin`, `interval_minutes=5`, `horizon_minutes=60`, `input_points`, `history_points_used=288`,
`model` и ровно 12 `points`. У каждой точки есть `timestamp`, `p10`, `p50`, `p90`.
`input_points` — число принятых измерений, `history_points_used` — длина истории
на входе модели. `forecast_origin` — последнее измерение, а первая прогнозная точка наступает
через 5 минут после него. При разрешённой задержке датчика начало прогноза
может оказаться в прошлом относительно момента ответа; клиент должен показывать
временные метки и давность исходного измерения.

`p50` — медиана. p10–p90 — номинальный 80%-й интервал, покрытие которого ещё
нужно проверить на реальных данных. Для `persistence` обе границы равны `null`.
Поле `model.clinical_validity` всегда равно `not_evaluated`.

| HTTP | Код ошибки / причина |
|---|---|
| 400 | `invalid_request`: некорректный JSON; `invalid_content_length`: неверная длина |
| 401 | `unauthorized`: нет корректного сервисного токена |
| 413 | `request_too_large`: тело больше 256 КиБ, в том числе при передаче частями |
| 415 | `unsupported_media_type` / `unsupported_encoding`: неверный тип или сжатое тело |
| 422 | `invalid_request`: схема; `invalid_history`: дубли, разрывы, недостаточная история |
| 422 | `signal_quality_rejected`, `stale_observations`, `future_observations` |
| 429 | `inference_busy`: уже идёт вычисление; заголовок `Retry-After: 1` |
| 503 | `model_unavailable` / `inference_failed`: модель не готова или произошёл сбой |

Форма ошибки: `{"error":{"code":"stale_observations","message":"..."}}`.
Ошибки валидации не возвращают полученные значения и исходное тело запроса.
Встроенная блокировка ограничивает число вычислений до одного на процесс;
это не пользовательские квоты и не распределённый rate limit.

## Границы интеграции

Bearer-токен здесь является ключом внутреннего сервиса. Его держат на основном
сервере, который аутентифицирует пользователя и проверяет владельца измерений.
В мобильное приложение общий сервисный ключ встраивать нельзя.
В этой версии пользовательских аккаунтов, проверки владения, BLE-адаптера,
клинических правил и публичного HTTPS-развёртывания ещё нет.

Процесс по умолчанию слушает только loopback. Для будущего развёртывания нужны
основной сервер с авторизацией, закрытый сетевой доступ к прогнозному сервису,
HTTPS на внешней границе и измеренные лимиты на конкретном оборудовании.
