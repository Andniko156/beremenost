# Дообучение Chronos-2: первый этап и продолжение

Исследовательская адаптация на реальной материнской ЧСС выполнена.
Сохранены LoRA-адаптер, полная локальная модель, происхождение данных,
разбиение по женщинам и результаты. Автоматического переключения API нет.

## Данные и постановка

Источник: [HRV and salivary cortisol data in pregnant women](https://zenodo.org/records/7102622),
DOI 10.7280/D12Q4P, CC0. Зафиксирован SHA-256 исходного Excel:
`bed2512b7b99c9a4c69f4c6fe61e3a698abe53208fe36e602755edfca4b3ac8a`.

В наборе 29 беременных 28–32 недель; 816 строк двух визитов. Используется
только ECG-derived `hr_ibi`. Кортизол, метки стресса и HRV не являются входами.
Одна невалидная HR-точка исключена; разрывы разделяют последовательность.
Интерполяции и вымышленных календарных времён нет: сохранён относительный
индекс исходного пятиминутного окна. Разные визиты не склеиваются.

Короткие стрессовые визиты содержат лишь шесть точек; для часовой цели
использованы 29 подходящих последовательностей контрольных визитов.
Контекст этого отдельного эксперимента — **6 × 5 мин = 30 мин**, цель —
**12 × 5 мин = 60 мин**. Нынешний API по-прежнему требует 24 часа истории.
Новый эксперимент не является проверкой качества API на суточной истории.

Seed 42 фиксирует разбиение: **20 женщин train, 4 validation, 5 test**.
В train 102 перекрывающихся окна из 20 женщин; число окон не равно числу
независимых пациенток. В validation/test берётся последнее полное окно
каждого подходящего сегмента: 4/5 часовых окон. Женщины не пересекаются.
Исходные данные, веса и индивидуальные прогнозы не добавляются в Git.

## Фактический запуск 4 ноября 2026

- Базовая модель: `amazon/chronos-2`, revision
  `29ec3766d36d6f73f0696f85560a422f50e8498c`.
- LoRA: rank 8, alpha 16; 1 206 912 обучаемых параметров из 120 684 576.
- 100 шагов, batch size 4, learning rate 1e-5; CPU, 4 потока, float32.
- Контрольная точка выбиралась по validation loss, проверка каждые 25 шагов.
  Выбрана checkpoint-100. Тестовые женщины не участвуют в выборе.
- Trainer сообщил 23,49 с обучения; полный этап с загрузкой модели и
  проверками — 57,62 с. Это замер малого эксперимента на данной машине.
- Проверено изменение LoRA-параметров и неизменность исходной модели.
- chronos-forecasting 2.3.2, transformers 4.57.6, peft 0.18.1,
  torch 2.8.0+cpu. Без PEFT команда завершится ошибкой: незаметный переход
  к полному обучению запрещён.

### Независимый тест: 5 женщин, 60 прогнозируемых точек

| Метод | MAE, уд/мин | RMSE, уд/мин | Покрытие p10–p90 |
|---|---:|---:|---:|
| Исходная Chronos-2 | 4,5131 | 5,7835 | 83,3% |
| Chronos-2 после LoRA | 4,5766 | 5,8228 | 80,0% |
| Последнее значение | 4,8133 | 6,2976 | Не оценивается |
| Среднее доступной истории | 5,2044 | 6,4264 | Не оценивается |

На validation MAE снизилась с 2,4738 до 2,3915, но на test стала примерно
на 1,4% выше. Поэтому версия сохранена как экспериментальная; преимущества
над исходной моделью по основному критерию нет. Настройки не подбирались
повторно по тестовым результатам. При пяти женщинах точность и покрытие
не дают основания для клинического вывода. Это спокойные лабораторные
визиты, без проверки осложнений, движения, VivaLNK и домашнего наблюдения.

Полный сводный результат: [results/hrv29_lora_v1.json](results/hrv29_lora_v1.json).

Следующий этап проверки выполнен на 24 development-участницах с отдельным
внутренним выбором настроек; прежние пять тестовых женщин исключены.
Протокол и результаты: [model_study.md](model_study.md). Начиная с версии 0.4,
`finetune` выбирает checkpoint по MAE прогноза на validation с равным весом
женщин. Для воспроизведения исторического запуска ниже явно указан
`--selection-metric eval_loss`.

## Воспроизведение

PowerShell, Python 3.12:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install torch==2.8.0 --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe -m pip install -e ".[finetune,test]"
.\.venv\Scripts\python.exe -m pregnancy_monitor prepare-hrv29 --output-dir data/hrv29
.\.venv\Scripts\python.exe -m pregnancy_monitor finetune --dataset data/hrv29 --output-dir outputs/hrv29_lora_v1 --steps 100 --batch-size 4 --cpu-threads 4 --selection-metric eval_loss
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Linux/macOS: заменить `.\.venv\Scripts\python.exe` на `.venv/bin/python`.
При подготовке можно передать `--input path/to/reviewed.xlsx`; проверка
контрольной суммы обязательна. Выходные каталоги должны быть новыми/пустыми:
существующие результаты не перезаписываются.

Получаются `data/hrv29/manifest.json` и `segments.json`; в каталоге запуска —
`adapter/`, `merged-model/`, `report.json`, `dataset_manifest.json`,
`trainer_history.json`, `training_lineage.json` и прогнозы validation/test.
Базовые модели сравниваются на тех же историях и будущих точках.
Cross-learning между женщинами при прогнозировании отключён.

## Сохранённые веса и следующий этап

Небольшой ZIP из чата содержит **LoRA-адаптер**, отчёт, манифест и происхождение
модели. Это не полный автономный Chronos-2: для восстановления нужна базовая
модель указанной ревизии, загруженная с Hub или находящаяся в локальном кеше.
Полная локальная модель текущего запуска находится в `merged-model/`.

После распаковки переносимого архива восстановить полную модель:

```powershell
.\.venv\Scripts\python.exe -m pregnancy_monitor export-adapter --input checkpoints/hrv29_lora_v1/adapter --output-dir models/hrv29-stage1
```

Флаг `--offline` требует заранее закешированной базовой модели.
Проверено, что адаптер и полная модель загружаются заново и дают совпадающие
прогнозы с численной погрешностью менее 0,0001 уд/мин.

После получения выгрузки медорганизации:

1. Согласовать формат и применимые права; получить стабильные псевдонимы
   женщин, сеансы, время измерения, единицы, срок беременности, устройство/
   ревизию и признаки качества. Диагнозы нужны для отдельной задачи событий,
   но не для обычного числового прогноза следующего HR.
2. Добавить конвертер именно фактической выгрузки в подготовленный формат
   schema v1: manifest и раздельные непрерывные segments. Требуемые поля
   показаны в `research_data.py`. Не подменять пропуски нормальными числами.
3. Выбрать по реальным данным профиль истории, сетку и горизонт. Для возврата
   к 24 часам нужны 288 точек контекста и 12 будущих при шаге 5 минут.
4. Сохранять стабильный `subject_namespace` и ID женщин во всех этапах.
   Lineage удерживает прежних тестовых женщин вне обучения и validation;
   прежние validation-женщины не должны попасть в train. При смене системы
   псевдонимов автоматическое обнаружение совпадений невозможно.
5. Запустить новый этап с полной сохранённой моделью как родителем:

```powershell
.\.venv\Scripts\python.exe -m pregnancy_monitor finetune --dataset data/medical/prepared --init-model models/hrv29-stage1 --output-dir outputs/medical-stage2 --steps 100
```

Конвертер медицинского формата и выбор подходящего бюджета выполняются после
получения фактических файлов. Это продолжение адаптации весов с новым
оптимизатором и новым LoRA, а не восстановление старого состояния Adam.
Следующий адаптер ссылается на полную родительскую модель; для его переноса
потребуется сохранить и родителя либо экспортировать новый merged-model.

Сравнить на медицинской когорте исходную базу, этап HRV29, новый этап и простые
прогнозы. Учитывать разницу устройств и условий. До сравнения нельзя считать,
что адаптация на 29 участницах полезнее старта с исходной Chronos-2.
Изменение медицинских порогов относится к отдельным правилам и проверке;
модель не обучается диагностировать осложнения по этому набору.
