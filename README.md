# Сохраняя главное — Chronos‑2 и экспериментальный API

Готовая `amazon/chronos-2` без дообучения прогнозирует числовой ряд пульса на
**60 минут**. Есть эксперименты из CSV и приватный локальный HTTP API.
Интерпретация результатов отдельной моделью и мобильное приложение — следующие этапы.

Версия 0.5 включает benchmark, проверку пригодности данных для живого прогноза,
API и исследовательское дообучение с разделением по женщинам, проверкой контекста
и прошлыми HRV-признаками. Начните с
[запуска API и демонстрации](docs/api.md) или [сравнения прогнозов](docs/benchmark.md).

Первый показатель — пульс в уд/мин. Пока конкретная модель VivaLNK и доступные
ей измерения не подтверждены, интеграции с датчиком здесь нет. Собственных
данных медорганизации пока нет; для исследования используется открытый HRV29.
Генератор создаёт исключительно синтетическую инженерную фикстуру.

Прогноз числового показателя не устанавливает диагноз, состояние плода или риск
осложнений. Медицинские пороги и рекомендации этот эксперимент не выдаёт.

## Что уже реализовано

- Проверка входного CSV: часовой пояс, числа, регулярность, дубли, объём истории.
- Настоящий адаптер `Chronos2Pipeline.predict_quantiles`, CPU или CUDA.
- Начальная конфигурация: шаг 5 минут, 288 наблюдений истории, 12 шагов прогноза.
  Это параметры эксперимента, а не подтверждённые требования датчика.
- Квантили p10 / p50 / p90. p50 — медиана; диапазон p10–p90 — номинальный
  80%-й прогнозный интервал модели. Его фактическое покрытие нужно измерять.
- Проверка на последовательных отложенных часовых окнах и сравнение с правилом
  «повторять последнее значение»: MAE, RMSE, покрытие и ширина интервала.
- Версия библиотеки и ревизия весов зафиксированы; результаты содержат конфигурацию.
- Тесты, в том числе на утечку будущего в историю и разделение рядов.
- Расширенное сравнение с последним значением, средним за час и предыдущим днём;
  ошибки отдельно на 5, 10, …, 60 минутах, по окнам и по каждому ряду.
- Локальный FastAPI: сервисный Bearer-токен, технические проверки качества,
  ограничение размера запроса и одного одновременного вычисления.

Результаты фактического запуска: [проверка первого эксперимента](docs/first_experiment.md).
Расширенная проверка: [второй эксперимент](docs/second_experiment.md).

## Первый запуск: Windows PowerShell

Нужен Python 3.10+; для начала рекомендуем Python 3.12.
Все команды выполняются из папки репозитория. Активация окружения не требуется.

```powershell
git clone https://github.com/Andniko156/beremenost.git
cd beremenost
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install torch==2.8.0 --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe -m pip install -e ".[chronos]"
.\.venv\Scripts\python.exe -m pregnancy_monitor generate
.\.venv\Scripts\python.exe -m pregnancy_monitor forecast --input data/synthetic_hr.csv --data-kind synthetic
.\.venv\Scripts\python.exe -m pregnancy_monitor backtest --input data/synthetic_hr.csv --data-kind synthetic
```

Установка зависимостей и первая загрузка весов требуют интернета. Веса занимают
около 478 МБ; зависимости PyTorch скачиваются отдельно. Время запуска на CPU
зависит от оборудования. На первом запуске модель загружается с Hugging Face,
после загрузки сам прогноз вычисляется локально; значения ряда в облачный API
прогноза не отправляются. Доступ к источнику скачивания из конкретной сети в РФ
нужно проверять отдельно.

Linux / macOS: создайте окружение `python3.12 -m venv .venv` и замените
`.\.venv\Scripts\python.exe` на `.venv/bin/python` в командах выше. Пример CPU
установки PyTorch выше предназначен для Windows/Linux; на macOS установите
`torch==2.8.0` из обычного индекса PyPI. Выбор CUDA требует совместимой сборки
PyTorch; параметр эксперимента — `--device cuda`.

## Где смотреть результат

`outputs/forecast/predictions.csv` содержит 12 будущих точек для каждого ряда.
Колонки: `series_id`, `timestamp` (UTC), `p10`, `p50`, `p90`, `backend`,
`forecast_origin` и `horizon_step`.
`outputs/forecast/report.json` содержит настройки и сведения о модели.

`outputs/backtest/report.json` содержит ошибки в уд/мин по всей выборке и
отдельно по каждому ряду. `outputs/backtest/predictions.csv` содержит прогнозы,
отложенные фактические значения и номера окон. В каждом окне модель видит
только предшествующие 288 наблюдений; следующие 12 используются для оценки.
По умолчанию проверяются последние 3 непересекающихся часа каждого ряда.

MAE — средняя абсолютная ошибка; RMSE сильнее учитывает крупные ошибки.
Низкая ошибка на синтетике показывает работу вычислительного конвейера,
но не доказывает точность на реальных измерениях или пригодность для медицины.
Даже победа над простым прогнозом на этой фикстуре не является критерием приёмки модели.

## Проверка без скачивания модели

```powershell
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m pregnancy_monitor generate
.\.venv\Scripts\python.exe -m pregnancy_monitor backtest --input data/synthetic_hr.csv --backend persistence --data-kind synthetic --output-dir outputs/baseline
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

`persistence` — отдельный простой прогноз. Он явно помечается в результате и
не подменяет Chronos‑2 при ошибках. Прогнозные интервалы для него не рассчитываются.

## Входные данные и ограничения

```csv
series_id,timestamp,heart_rate_bpm
synthetic_001,2026-01-01T00:00:00Z,75.0
synthetic_001,2026-01-01T00:05:00Z,75.4
```

Нужно минимум 288 наблюдений на ряд для прогноза и 324 для проверки с 3 окнами.
`series_id` — псевдоним; ФИО, контакты, ЭКГ и дневник симптомов сюда не передаются.
Если исходный датчик выдаёт измерения чаще, отдельный адаптер должен подготовить
ряд с согласованной агрегацией и контролем качества. Этот код **не** усредняет,
не интерполирует и не заполняет пропуски автоматически. Дубли и разрывы приводят
к ошибке. Нерегулярные измерения давления нельзя выдавать за регулярный ряд пульса.
Дополнительные колонки отклоняются, чтобы случайно не передать их как признаки модели.

Прогноз начинается после последней точки файла, а не после текущего времени.
CLI сохраняет этот режим для исторических экспериментов. В API проверяются
давность данных и переданные адаптером отметки качества; плохие и неизвестные
отметки приводят к отказу. Детектор артефактов движения и качества контакта
конкретного VivaLNK ещё требуется разработать на основе его SDK и измерений.

## Работа на своём сервере без обращения к Hub

Сначала на машине с доступом к Hugging Face сохраните точную ревизию:

```powershell
.\.venv\Scripts\python.exe -c "from huggingface_hub import snapshot_download; snapshot_download('amazon/chronos-2', revision='29ec3766d36d6f73f0696f85560a422f50e8498c', local_dir='models/chronos-2')"
```

Перенесите папку `models/chronos-2` на сервер. Зависимости также должны быть
установлены заранее (для изолированной установки нужен отдельный wheelhouse
под ОС и Python сервера). Затем:

```powershell
.\.venv\Scripts\python.exe -m pregnancy_monitor forecast --input data/synthetic_hr.csv --model models/chronos-2 --offline --data-kind synthetic
```

Для локальной папки ревизия не выводится из имени: сохраните её происхождение
при переносе. Копию весов можно держать на сервере в РФ. HTTP API описан
в [docs/api.md](docs/api.md); публичный сервер и база персональных данных
в этой версии не развёрнуты.

## Первое дообучение на данных беременных

Добавлены подготовка HRV29 с разделением по женщинам, LoRA-дообучение и
сохранение версии для следующего этапа на данных медорганизации.
Реальный запуск: 100 шагов, 20/4/5 женщин в train/validation/test;
30 минут истории → прогноз на час. На тесте MAE исходной Chronos-2 —
4,51 уд/мин, после LoRA — 4,58. Улучшение точечного прогноза не подтверждено,
дообученная версия автоматически в API не применяется.

Команды, результаты и продолжение с сохранённых весов:
[docs/finetuning.md](docs/finetuning.md).

## Оценка и выбор модели без повторного подбора по тесту

Команда `study` сравнивает исходную Chronos-2 с более осторожным LoRA и
их смесями на 24 development-участницах. Пять прежних тестовых женщин
исключаются. В каждом внешнем разбиении параметры выбираются на отдельной
внутренней валидации; checkpoint выбирается по ошибке прогноза ЧСС.
Исходная модель остаётся допустимым выбором. Подробный протокол и результаты:
[docs/model_study.md](docs/model_study.md).

Следующий эксперимент `ablation` добавляет сравнение длины истории, прошлые
RMSSD/SDNN, Ridge и четыре варианта LoRA на трёх повторных разбиениях.
Основной дополнительный профиль — час истории → 30 минут прогноза;
часовая задача и сравнение более длинной истории рассматриваются отдельно.
Протокол и запуск: [docs/ablation_study.md](docs/ablation_study.md).

## Дальнейшая работа

1. Запустить эксперимент на целевом компьютере и зафиксировать время и память.
2. Подтвердить модель VivaLNK, SDK, единицы, частоту и экспорт реальных измерений.
3. Собрать разрешённую обезличенную выборку; согласовать политику пропусков
   и качества сигнала. Сравнить модель с простыми прогнозами на будущих окнах
   и на участницах, которые не использовались при настройке.
4. Согласовать с врачом задачу и критерии клинической проверки; лишь затем
   обсуждать медицинские выводы. Не обучать на синтетике ради видимости качества.
5. Подключить к приватному прогнозному API основной сервер с пользовательской
   авторизацией и клиент Flutter. План этапов: [development.md](docs/development.md).
   Продолжить адаптацию сохранённой исследовательской версии после получения
   разрешённой профильной медицинской выгрузки и повторной проверки качества.
